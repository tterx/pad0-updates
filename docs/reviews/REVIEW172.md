# v101.172 030 시작점 불일치와 실패 후 UP 우선 정리

## 첨부에서 확인한 것

261023_091954_이동_030.zip은 v101.171이며 실제 선택 장치 ID 3, SOURCE_TOUCHSCREEN(4098)을 기록했습니다. 예정 시작점은 19번 빨강, 네이티브 좌표 (1266,738)입니다. 지정 드롭은 변하지 않았고 held.png에는 다른 위치의 보라 드롭이 들린 모습이 있습니다. 시작점 확인 세 번 후 약 1.637초에 시간 예산이 부족해졌습니다. MOVE는 0회입니다. 이전 029의 전체 MOVE 후 판 불일치와 다른 실패 단계입니다. 장치 ID 통일만으로 이 문제가 해결되지 않았습니다.

전달 기록은 DOWN 1회와 CANCEL 1회뿐입니다. 정리 함수가 CANCEL을 먼저 보내 Android의 터치 대상을 없앤 뒤 UP을 보내므로, 그 UP은 거부될 수 있습니다. 실제 기록에도 전달된 UP은 없습니다. Android TouchStates는 정리 전후 idle이지만 게임의 해제를 뜻하지 않습니다. 게임이 CANCEL을 처리하지 않는지, 어느 입력 경로가 다른 위치를 선택하는지는 이 ZIP만으로 확정할 수 없습니다. 사용자는 PAD0와 MuMu를 모두 재시작한 뒤 시험했다고 확인했습니다. 과거 실행의 잔류 입력만으로 이번 재발을 설명하지 않습니다. 화면에 보인 드롭을 무조건 실제 좌표 변환값으로 삼아 오프셋을 바꾸지 않습니다.

## 수정

- 드래그의 legacy IInputManager binder 직접 호출을 제거합니다. Android 표준 input 명령이 사용하는 InputManagerGlobal 또는 구버전 InputManager의 injectInputEvent 래퍼를 거칩니다. 최신 Android 래퍼는 injectInputEventToTarget으로 전달하므로 장치 ID만 같았던 v171보다 실제 UI 입력의 호출 경로에 맞춥니다. API가 없거나 실행이 실패하면 옛 binder로 몰래 대체하지 않습니다. 선택 API는 touch_input_api에 기록합니다. 이 차이가 잘못된 시작점의 원인이었다고 확정하지 않습니다.
- 실패·F10·연결 종료·터치 기한 만료에서 남은 MOVE를 멈춘 뒤, 소유한 터치의 같은 장치/좌표/누름 시각으로 UP을 먼저 보냅니다. 성공하면 추가 CANCEL/UP을 보내지 않습니다. UP 실패 때만 CANCEL을 시도하고 최초 UP 실패를 유지합니다. CANCEL 성공은 Android 정리 근거로만 기록하며 게임이 정상 UP을 받았다고 승인하지 않습니다. idle 정리에는 이벤트가 없습니다.
- 지정 시작점이 픽셀 기준 그대로이고 멀리 떨어진 셀만 크게 바뀌며 24개 이상 셀이 안정적이면 시작점 불일치로 즉시 중지합니다. 이는 실패를 빨리 검출하는 음성 근거입니다. 다른 셀을 성공한 시작점으로 대체하거나 좌표를 보정하거나 새 DOWN을 재시도하지 않습니다. 전체 밝기 변화, 정지 화면, 작은 커서 흔들림은 이 조건과 구분합니다.
- 일반 실패 후에는 실제 해제 뒤 화면을 released.png로 별도 저장합니다. 시작점 확인처럼 MOVE가 없었던 경우 최대 세 프레임에서 원래 판이 복원됐는지 기록합니다. 정상 UP 응답만으로 게임 해제를 단정하지 않습니다. 이미 MOVE가 있었던 실패는 그 화면을 원래 판 복원 성공으로 해석하지 않습니다. F10으로 취소된 뒤에는 캡처하지 않습니다.
- 실패 전 held/failure/after.png를 덮어쓰지 않습니다. 최초 이동 오류와 UP/대체 CANCEL 결과, 해제 후 화면을 구분합니다. ADB 단독 실행과 실제 판 확인은 유지합니다.

이 버전은 잘못된 시작점의 전체 원인과 실제 MuMu 재발 해소를 확정하지 않습니다. 알려진 실패 정리 순서를 수정하고 다음 기록에 실제 해제 후 관찰을 남깁니다. 사용자가 이미 두 프로그램을 재시작했다는 조건을 재현 전제로 유지합니다. 단순 재시작을 해결책으로 제시하지 않습니다. AI 재학습이나 ADB 주소 재설정은 필요 없습니다.

## 검증 설계

실제 Java 실행기와 시험 Android API에 ‘Android CANCEL은 처리하지만 게임은 UP에만 반응’하는 정책을 둡니다. 소유한 DOWN → UP, idle 추가 이벤트 없음, UP 실패/CANCEL 성공 시 게임 해제 성공으로 보고하지 않음을 검증합니다. 이는 가능한 실패 형태를 검증하는 시험 모델이며 실제 Unity 구현을 역으로 확인한 증거는 아닙니다.

실제 030 game/held 이미지로 19번 그대로·21번 변화·28셀 안정 조건을 재현합니다. 첫 확인 후 MOVE 0회/UP 1회, 별도 복원 이미지, 복원되지 않은 경우 최대 세 번 관찰, F10 뒤 캡처 없음과 최초 오류 유지 검사를 추가합니다. 기존 정상 경로·중지·기한 만료·거부·구름·들린 최종 드롭·배포 모듈 검사도 유지합니다.

검사 수를 줄이려고 고유 조건을 삭제하지 않습니다. v170 CANCEL 우선의 기대를 소유한 UP 우선으로, v171 실패 경로의 CANCEL/UP 기대를 UP 한 번으로 갱신합니다. 기존 프로토콜 필드와 공통 자료 형식·모듈 경계·의존성은 유지하며, 선택 API용 읽기 전용 조회 명령 7과 새 내장 실행기 파일명으로 구분합니다. 두 OS 래퍼 선택과 legacy binder 직접 호출 금지도 실제 Java/시험 Android로 확인합니다. 실제 Windows/MuMu는 이 개발 환경에 연결돼 있지 않습니다.
