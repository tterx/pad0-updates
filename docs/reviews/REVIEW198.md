# v101.198 일정 간격 전송 및 지연 진단

GitHub main 99b633c(v197), pad0_input.py, pad0_overlay.py, REVIEW194~197 및 공식 MaaFramework 전송 구현을 기준으로 검토했습니다.

## 코드에서 확인한 사항

v197은 각 MOVE post 뒤 Job을 1ms 폴링으로 완료 확인했습니다. 간격은 실제 요청 시각 기준이므로 Job 비용이 18.75ms 안에 끝나면 그 비용을 다시 더해 기다리는 구조는 아니었습니다. 따라서 Job 대기만을 느린 움직임의 확정 원인이라고 할 수 없습니다. 기존 ZIP의 DOWN Job 대기는 약1.3ms이며, MOVE/Android 실행 지연은 이를 근거로 확정할 수 없습니다. Python 스케줄링·큐·파이프 쓰기·Android 주입·게임 프레임 처리는 서로 다른 단계입니다. v197 로그는 요청과 완료를 충분히 구분하지 못했습니다.

4개 보간은 각 칸 중심을 정확히 지나고 왕복 경유점을 보존합니다. 보간 개수 자체가 문제라는 증거가 없어 유지합니다. 각 MOVE마다 프로세스를 생성하지 않으며 기존 컨트롤러가 지속 파이프로 전송합니다. 코너 곡선/칸 생략/선행 명령 일괄 큐잉은 추가하지 않습니다.

## 변경 흐름

이전: 예정 간격 대기 → post MOVE → 즉시 Job 폴링 → 다음 예정 간격.
현재: 예정 간격 대기 → 직전 MOVE Job 완료 장벽 → 실제 요청 시각 기록 → post MOVE → 다음 예정 간격. 미완료 MOVE는 최대1건입니다. ACK가 늦으면 다음 요청이 늦어지고 이후 일정은 그 실제 시각에서 새로 잡습니다. 밀린 이벤트를 몰아 보내지 않습니다. 전송 실패/중지는 새 DOWN 없이 원래 컨트롤러 UP을 시도합니다. 최종 MOVE 완료를 확인한 뒤 캡처와 기존 손 떼기 전 판 안정 확인을 수행합니다.

직접 MaaTouch 채널은 추가하지 않았습니다. 공식 API가 일정 간격을 감당하지 못한다는 실기 근거가 없고, 057은 요청 칸 변화 없이 다른 칸이 들린 사례이므로 별도 채널로 속도만 바꾸는 것은 좌표 문제를 해결하지 않습니다. 두 소유자의 중복 입력 위험을 추가하지 않고 기존 컨트롤러 한 개로 순서와 해제를 유지하는 방안A를 적용했습니다.

MaaTouch 기본/복원값을18.75ms, 코너 추가0ms로 맞춰 명목상75ms/칸을 목표로 합니다. 사용자가 저장한 간격은 유지하므로 기존25/27.5ms 설정은 속도 조절창에서 변경해야 합니다. SDK 선택과 방식별 시간 예산을 유지합니다. 시작 확인/정착/캡처 시간은75ms에 포함되지 않습니다. Windows 스케줄링과 실제 게임 소비 때문에 실기75ms를 보장하지 않습니다.

## 좌표와 안전

입력 직전 컨트롤러 원본 해상도와 캡처 해상도를 대조합니다. 기존 시리얼·캡처 동일 기기 확인, 시작 칸 중심/native DOWN 비교 및 시작 드롭 화면 확인을 유지합니다. 요청 칸이 그대로이고 다른 칸이 변했다는 부정 증거는 두 번째 읽기부터 중단에 사용하며 새 DOWN을 보내지 않습니다. 057의 회전/스케일/잔류 접점 중 어느 원인인지는 여전히 미확정입니다. 회전값이나 위치를 추측해서 보정하지 않습니다. SDK 자동 전환도 없습니다.

## ZIP 진단

input_display.move_schedule: 목표 간격, PC 요청 간격 최소/중앙/최대, 각 요청의 목표/실제 시각과 좌표, 누적 국소 지각 합, 칸별 소요시간, 코너 대기 및 요청 간 공백, DOWN/UP 기록을 보존합니다. input_display.input_pipeline에는 컨트롤러ID·기기·원본크기·좌표 설정·각 API 좌표·post 호출 비용·장벽 대기·완료 관찰 시각을 기록합니다. 두 시계 원점은 perf_counter 값으로 명시합니다. 기존 execute_seconds와 시작/마지막 판 검증 및 실패 화면을 유지합니다.

모든 시각은 PC 측입니다. completion_observed는 다음 장벽에서 완료를 관찰한 시각으로 실제 Job 완료 시각의 상한이며 Android 실행 시각이 아닙니다. API post 비용과 장벽 대기는 Android 주입 지연을 측정하지 않습니다. backend_transformed_coordinates 및 android_execution_timestamps는 관측할 수 없어 null로 기록하며 raw/API 좌표를 실제 Android 좌표라고 주장하지 않습니다. 게임 반영 근거는 별도의 시작/최종 판 검증뿐이며 각 중간 MOVE의 Android 수신 ACK는 없습니다.

자동 속도 시험·실기 반복 조작·시뮬레이션을 추가하거나 실행하지 않았습니다. 검토와 구문/패키지 정합성만 확인했습니다. 실기에서는18.75ms/코너0 설정으로 한 번 실행하고, 칸 누락·왕복/코너 끊김·다른 칸 들림·F10 후 해제를 확인하세요. 실패 ZIP의 실제 요청 공백/장벽 대기/판 검증으로 다음 원인을 좁힐 수 있습니다. SDK 동등 속도와 안정성은 실기 미검증입니다.
