# v1.0.50 / updater258

The previous error-save action was tied to the last explicitly captured/displayed puzzle. Passive condition confirmation could fail before any such capture existed, so saving either refused or exported the last played board. Adding scalar condition history in257 did not provide the failed probe's source pixels. That was insufficient for diagnosing the current `조건 다시 확인` state.

The passive probe now keeps its own in-memory copy of the whole game frame and matching board crop before OCR. It verifies the crop's board against the requested probe, associates the pixels with the current board/area/party/epoch and probe serial, and records actual OCR exceptions, raw condition/timer evidence and bounded read history. Health-only samples do not replace this evidence; newer unmatched captures invalidate the old serial. HP-only preference changes do not change party identity. No file or screenshot is created by keeping this RAM evidence. If capture itself fails before pixels exist, a metadata-only failure with the actual exception is saved; no prior image is substituted.

The floating HUD exposes `조건 오류 저장` when a matching failure is available. This action saves the cached failed frame directly, including before the first move and while preparation is still busy, with an empty path and `manual_condition` provenance. It never captures a new screen, starts a solver or sends input. Missing/stale condition evidence produces a clear refusal and cannot fall back to a previous play. The existing main-window error button also prefers a matching current condition failure; normal move/reward diagnostics otherwise retain their original flow. These archives have a distinct `조건` filename category and share the existing monotonic sequence.

Report130 is a successful v1.0.49 move with retained initial history: unknown time/enemy conditions after4.031 seconds, then4.469 seconds in the extra window, followed by a confirmed8-second five-attribute/six-combo move. Its source snapshots do not establish the exact first OCR/capture exception. Version257's queued execution continuation made re-confirmation proceed directly into movement when preparation became ready. Preparation now only announces readiness; it cannot resume a previous execution click. Recalculation in other modes explicitly passes a prepare-only flag through the existing solver callback. Actual movement requires a fresh upper execution press on a prepared path and retains the existing board/timer/condition validation.

Sixteen regressions cover saving before the first move, distinguishing previous play, source-copy stability, missing/stale rejection, HP identity, raw probe exceptions, bounded history, no new capture/input, legacy move saves, real Tk button behavior and prepare-only requests. Existing manual recovery checks now assert that re-confirmation never invokes execution. Physical MuMu interaction is not replayed. User images and diagnostic ZIPs are not published.
