# v1.0.55 / updater263

Report136 is v1.0.54 and records unknown-condition wait windows of12.484 and12.125 seconds. It contains only the recognized board image, no full-game capture, no timer/combo readings and no probe stage. Therefore it establishes a24.609-second recorded wait, not the exact blocking call. The subsequently supplied screenshot visibly shows8 seconds, the party six-combo goal and no obvious enemy combo-absorption badge; it does not establish which program call was stalled.

Inspection found two reproducible blocking mechanisms. Manual timer capture already obtains visibility-checked desktop pixels but then synchronously initializes the selected device/capture backend, whose connection and capture startup can outlive both condition wait windows. Separately, a single shared busy flag survives without a current-board job identity; obsolete work can block a new board, and a stale queue completion can clear a newer job's busy state. These are tested candidate mechanisms, not a claim that136 proves either one occurred.

Optional connected capture now has a150ms foreground wait budget. At expiry or while a previous request is still pending, condition/execution checks continue with the current visibility-checked desktop capture. Only one optional backend request may remain pending, its late result is discarded, and each later request has an independent result queue. A fast, currently verified selected-device capture remains eligible. Existing foreground, occlusion and minimization checks run before either source, and all board/time/combo/spike validation still runs on the selected frame. An unread condition still blocks input; no guessed time or enemy requirement is added. Backend touch is deferred as before; automatic farming/input transports are unchanged.

Every scheduled probe now has a board/rectangle/party/safety identity, action/recognition epochs and a serial. Parent processing retires orphaned or obsolete jobs before starting the current board's probe; only the current job can clear its busy state or publish a result. Cancellation invalidates old jobs, and resumed old captures cannot overwrite a new probe. Only an obsolete condition-unknown latch is cleared, retaining successful previews and bounded solver failures. The existing12-second OCR watchdog remains bounded.

The route button now distinguishes game-screen acquisition, time recognition, enemy combo recognition and final-board verification. Even a recognized-board-only error report records the matching scheduled/running job stage and elapsed time. This makes the next failure diagnosable without interpreting the previous combined message as proof of a combo OCR stall.

Thirteen regressions cover a blocked backend with bounded desktop fallback, one pending request, late-result isolation, fast/failed/no-device captures, native minimization rejection, modeled136 orphan/terminal wait recovery, changed job identities, stale queued results, canceled/resumed workers, stage diagnostics and explicit-input preservation.
